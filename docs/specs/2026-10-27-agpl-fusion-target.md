## 产品定义

MemWeave 是已有编程 Agent 的本地连续工作层。它保存一个项目内任务如何开始、如何被中断、如何被接续，以及任务或阶段完成后哪些经验值得进入长期知识。

产品不以聊天记录、独立客户端或工具数量为中心。核心结果是：

1. 一个长时间任务经历多次上下文压缩，仍能继续。
2. 同项目新会话中的新 Agent 能接续当前任务。
3. Cursor 不可用后，Codex 打开同一项目仍能接续。
4. 任务或阶段收束后，下一次相关工作能使用此前提炼的知识。

## 产品层次

### 第一层：任务工作记忆

任务工作记忆保存：

- 目标和可验收条件。
- 约束、决策、发现、失败尝试与验证结果。
- 当前阶段、实际进展、唯一下一步。
- 相关文件、命令结果摘要和来源引用。
- 任务顺序、当前任务和未开始队列。

它必须跨模型上下文、跨会话、跨客户端存活。上下文压缩不是唯一中断点；任务状态应在阶段变化、失败、验证和切换客户端前持续写入。

同一项目只允许一个 `current` 任务。其余任务处于 `queued` 顺序队列。当前任务完成或取消后，下一个任务才成为当前任务。恢复入口不得按最近更新时间猜测。

单个 `current` 不限制并行执行。当前任务下可以有多个持久 WorkUnit，用于父 Agent 分派给子代理的独立工作流。每个 WorkUnit 至少保存：

- 所属任务、负责人/Agent 标识和简短范围。
- `pending`、`running`、`blocked`、`completed` 或 `cancelled` 状态。
- 发现、进展、下一步、改动范围和阻塞原因。
- 创建、更新顺序与独立 revision/etag，避免多个子代理并发覆盖父任务记录。

子代理共享父任务 ID，但只更新自己的 WorkUnit。父 Agent 汇总结果并负责任务检查点、验收与关闭；WorkUnit 不能被恢复入口误认成新的顶层任务。任务关闭前，必需 WorkUnit 必须完成、取消或由用户明确放弃。

WorkUnit 的独立 revision/etag 只保证记录级并发安全，不隔离工作树。多个子代理实际修改代码时，宿主必须使用独立 worktree 或互不重叠的文件范围；父 Agent 负责合并、整体验证和验收。任务顺序模型不能被解释为文件系统或 Git 合并自动协调。

同一 Git common directory 的主 checkout 与 linked worktree 属于同一项目和同一顺序任务队列；worktree 只作为执行根，不产生第二个 project 或 current。不同 clone 仍分别登记。worktree 可以在自己的目录安装受管 MCP、Skill 与 Hook，但安装根不同不等于项目身份不同；客户端必须显式报告并修复缺失的 worktree 安装，不能静默把会话留在无 MemWeave 状态。

### 第二层：长期知识

长期知识来自任务或阶段的真实证据，而不是聊天摘要或自动生成的项目简介。每条知识至少具有：

- 范围：项目、任务或用户明确偏好。
- 来源：任务、文件、用户或宿主观察。
- 状态：候选或已启用。
- 适用条件与可纠正说明。

任务完成或阶段收束都可以触发提炼；阶段提炼不要求关闭整个任务。候选知识默认不进入常规上下文，只有显式审核后才可启用。纠正、遗忘和来源漂移必须能让旧结论停止进入后续上下文。

**共享存储不等于跨项目可见。** 活动库可以只有一个 `%USERPROFILE%\.memweave`，但每条知识必须按适用范围过滤：

| scope | 可适用对象 | 边界 |
|---|---|---|
| `project` | 同一 `project_id` 的后续任务和新会话 | 不自动进入其他项目 |
| `task` | 指定 `task_id` 的任务 | 不进入其他任务或其他项目 |
| `user` | 用户明确要求长期保留的偏好或规则 | 来源必须包含 `user`；不能绑定 task；只有显式 `include_user=true` 才可读取，不能承载项目事实 |

任务、检查点、WorkUnit 和 phase 属于工作记忆，不得直接当作长期知识。`memory_review` 只返回任务/阶段证据和已有知识，不生成或提升知识；`memory_review_complete` 只记录审查结果。MCP 的 `memweave_memory_write` 默认写入 `candidate`，只有显式激活才进入默认检索。`knowledge/` 是 Markdown 权威记录，`index/basic-memory/` 只是可重建索引。项目事实不得为了“跨项目复用”而写成 user scope；只有用户明确要求的稳定偏好或规则可以使用 user scope。

### 支撑：项目结构与架构证据

文件结构和宿主提供的架构关系用于定位、核对记忆是否仍适用于当前代码，不是第三层记忆或独立产品主线。它们与任务和知识共享项目身份及关系查询；来源变化后不得静默当作有效结论。

## 形态与职责

最终产品形态固定为一个 MCP、一个 Skill、一个 Hook 入口：

| 组成 | 职责 |
|---|---|
| MCP | 统一项目、任务、检查点、阶段和长期知识的写入、检索与上下文接口；不承担模型理解 |
| Skill | 规定开始/恢复、执行、检查点、阶段收束、长期提炼、纠正和遗忘的工作循环 |
| Hooks | 在会话开始、用户提交、工具后、压缩、停止、中断和结束时触发恢复、标记或一次有界维护；不伪造业务完成 |

不允许以两个 MCP 服务、两个索引或两个上下文构建器作为最终集成方式。

## 技术与许可证

- 目标许可证：AGPL-3.0-or-later。
- 存储：Markdown 为权威记录，SQLite 为可重建的派生索引。
- 底座：直接 fork/改编 Basic Memory 的 Markdown 存储、索引、检索和上下文能力，保留 AGPL 来源与修改记录。
- 任务生命周期：直接移植/改编 planning-with-files 的 MIT 实现，保留 MIT 声明。
- 客户端：Codex 与 Cursor；两者读取同一项目记忆库。
- 理解与提炼：由当前宿主 Agent 完成；MemWeave 不独立调用模型，不要求额外模型 API 密钥。
- 入口：Agent 内工作流优先；CLI 辅助安装、诊断和维护；管理页只在需要查看、纠正或遗忘时使用。

## 统一记录模型

目标记录至少包括：

| 记录 | 关键字段 |
|---|---|
| Project | 规范根目录、标题、稳定 ID、客户端共享状态 |
| Task | 标题、目标、验收、状态、队列位置、当前阶段、下一步 |
| Checkpoint | 发现、进展、失败、验证、下一步、创建时间、来源 |
| WorkUnit | 所属任务、负责人、范围、状态、发现/进展/下一步、阻塞原因 |
| Phase | 所属任务、边界、结果、是否触发知识提炼 |
| Knowledge | 标题、正文、范围、来源、状态、适用条件、关系 |
| Source | 用户、文件、任务或宿主观测的可回读引用 |

任务、检查点、阶段、知识和结构证据共享项目身份与关系索引。删除或重建 SQLite 不能删除业务记录。

## 四个时点

| 时点 | 目标行为 | 用户参与 |
|---|---|---|
| 开始或恢复 | 恢复唯一当前任务；给出目标、验收、最新检查点、失败与下一步；宿主先核对用户目标和实际代码 | 当前目标明显不同；需要启用用户范围知识 |
| 执行 | 在阶段、发现、失败、验证和切换客户端前写检查点；上下文压缩后重新注入有界任务状态 | 影响行动的冲突或授权问题 |
| 阶段结束或任务完成 | 核对验收；从证据提炼、去重、修订知识；阶段收束不要求关闭任务 | 重要推断确认；超出原授权范围的保存 |
| 下一次相关工作 | 按当前目标和范围取回知识；尊重纠正、遗忘、来源漂移和客户端差异 | 历史知识与当前要求存在影响行动的歧义 |

## 上下文规则

统一上下文构建器按以下顺序分配预算：

1. 当前任务目标、验收、最新检查点、失败尝试和下一步。
2. 当前任务运行中、阻塞和最近完成的 WorkUnit 摘要。
3. 与当前目标相关的已启用长期知识。
4. 与当前文件、决策和验证相关的结构证据。
5. 来源、截断、覆盖和新鲜度说明。

长期知识、结构证据或历史检查点不得挤掉当前任务的唯一下一步。返回结果必须区分实际纳入、被截断和未扫描内容。

## 跨客户端规则

- 以规范项目根目录识别同一项目，不把不同客户端视为不同项目。
- 任务状态不依赖某个客户端的会话数据库、缓存或聊天历史。
- 客户端缺少某类事件时，走明确的主动 Skill/MCP 路径，不伪造自动触发。
- Hook 只有在真实客户端支持并验证后才可宣称自动恢复；配置和协议通过不等于桌面体验通过。
- 两个客户端读取同一 Markdown 记忆库和索引；客户端重载、Hook 信任和桌面验证分别记录。
- 同名全局与项目级 MCP 配置可能产生遮蔽。已验证的 Cursor `3.27.14` 路径使用全局同名服务；接入时应让两者指向同一 home，或只保留一个同名项。

## 压缩与恢复规则

- 任务状态必须在模型上下文之外持续存在；不能把全部希望寄托在压缩瞬间的一次保存。
- PreCompact 可以是观察或提醒事件，但不得伪造压缩摘要或宣称已保存。
- 恢复时只提供恢复候选；宿主必须核对当前用户目标、Git 状态和实际文件。
- 多个历史任务不能自动推断为当前任务；目标不同必须新建或显式选择，不得继承旧进度。

## 安全与隐私

- 不保存凭据、访问令牌、完整聊天记录、transcript 或无关个人数据。
- Hook 输入只在进程内用于本轮召回；不写入业务记录、收据、会话状态或日志。
- 记忆库默认面向可信本机单用户；记录 ID 不是远程访问凭证。
- 候选知识默认不进入上下文；遗忘删除当前记录和逻辑索引，不承诺清除外部备份或已发出的上下文。

## 验收标准

### 场景 1：长任务与多次压缩

在真实任务中制造至少两次上下文压缩和一次验证失败。恢复后，新上下文能指出目标、失败路径、当前阶段和唯一下一步，不重复已否定方案。

### 场景 2：同项目新会话

关闭会话后在同一项目开新会话。Hook 恢复唯一当前任务，宿主核对用户目标和实际代码后继续；不得把历史任务当成当前目标。

### 场景 3：跨客户端

在 Cursor 推进任务后停止，在 Codex 打开同一项目。Codex 能读取同一任务状态、队列和相关知识；不要求用户重新解释，也不依赖 Cursor 会话缓存。

### 场景 4：阶段后长期积累

完成一个阶段但不关闭任务，提炼一条有来源的知识；下一次相关任务能取回它，无关任务不自动注入；用户纠正后旧结论不再进入上下文。

### 工程与开源验收

- 一个 MCP、一个 Skill、一个 Hook 入口。
- 一个当前任务和顺序队列，无任务选择歧义。
- 一个当前任务内可并行多个 WorkUnit；子代理进度可恢复，父任务状态不会被并发覆盖。
- 删除 SQLite 后可重建索引；Markdown 记录仍可读。
- 0.2.5 可迁移数据有 dry-run、备份和结果说明。
- AGPL、上游来源、修改记录和第三方声明完整。
- 文档明确区分 0.2.5 现状与融合目标，不把计划写成已完成能力。

## 非目标

- 独立客户端、独立聊天应用或独立模型服务。
- 同项目并行推进多个当前任务。
- 最终保留两个 MCP 服务或两个上下文构建器。
- 把图谱做成独立第三层或新的独立引擎。
- 自研 Basic Memory 已有且许可证允许复用的语义/混合检索。
- 在真实场景通过前把安装、工具数量、页面或演示当作产品完成。
