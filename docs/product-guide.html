MemWeave 贯穿项目的整个生命周期

AI 推进一个项目时，上下文会满、会话会换、工具也会换。MemWeave 把任务做到哪、试过什么、下一步做什么记在本机，并把值得复用的经验沉淀下来，让下一次能接着干。

00 / 优势

长任务不跑偏，项目和经验都能接上

推进一个长任务时，上下文会越来越长，还会经历多次压缩。AI 可能忘记目标、重复试错，甚至偏离方向；如果中途换了会话或客户端，任务状态又断了。

三个直接好处

一个解决长任务跑偏，一个解决换会话/客户端断线，一个解决经验留不下来。

01 长任务不跑偏

任务做久了，AI 容易忘记目标、重复试错，甚至被中间细节带偏。

MemWeave 把目标、失败和下一步记在本机，每次压缩或新会话后都带回来，减少这种偏移。

长上下文→ 多次压缩→ 目标 / 失败 / 下一步

02 项目记忆跨会话、跨客户端

项目原本在一个工具里推进，下一次开新会话，或换到另一个 MCP 客户端，仍然接着同一个项目、同一个任务。

不需要重新解释目标、进度和失败；换的是工具或会话，不是任务。

工具 A→ 工具 B→ 同一个任务

同一个项目，同一个任务。

03 任务沉淀经验，用户记忆跨项目

每个任务结束时，把值得复用的结论审核后沉淀为项目经验；下次遇到类似工作，可以直接复用，不用重新摸索。

用户明确要求保留的偏好或经验，可以跨项目使用；只有显式启用才进入上下文。

任务结束→ 证据审查→ 项目经验

用户记忆：跨项目，显式启用。

一句话：MemWeave 不替你写代码。它把任务的目标、失败和下一步记在本机，让 AI 在长任务压缩后、换会话或换客户端时仍然能接着做；任务结束后，还能把项目经验沉淀下来。

01 / 项目

项目就是你打开的那个文件夹

多个客户端能接上同一个项目，前提是它们认的是同一个项目身份。项目身份不是客户端账号，也不是聊天会话，而是你打开的那个绝对文件夹。子目录可以再登记成独立项目；登记后它只读自己，不需要知道父项目。父项目本来就能看到全部代码，也可以直接当一个项目推进；需要快速了解已登记的子项目时，再读它们的摘要。

项目身份跟着文件夹走

客户端只是读取入口；同一个文件夹，不管从哪个工具打开，都是同一个项目。

不同客户端 AI 工具 A AI 工具 B AI 工具 C

一句话：同一个文件夹是同一个项目；登记子目录只是让它成为独立项目，不会让它依赖父项目。父项目可以直接当一个大项目推进，需要时再读子项目摘要。

02 / 任务

一次只推进一个主任务

任务不是一条待办，而是一份可恢复的契约：目标、验收、阶段、下一步和契约摘要。顶层任务顺序化，任务内部才并行；无关工作走侧任务，不抢主队列。

任务状态机

新任务进入 current 或 queued；current 完成后进入 completed，审查后归档；queued 在 current 关闭后补位。

side 侧任务

不进入主队列；完成后同样进入 completed 审查，取消后直接归档；关闭时不影响 current / queued。

phase 收束

只是阶段边界，current 不变，不关闭任务。

同一时间只有一个主任务。已有主任务时，新目标先排队；主任务完成或取消后，排在最前面的任务自动接上。侧任务有自己的目标、验收和进度，但不占主队列；阶段收束只结束一个阶段，任务状态不变。目标和验收被外部改动时，系统会提示先确认，不会悄悄按旧目标继续。

一句话：顶层任务顺序化，任务内部才并行；无关工作走侧任务，不抢主队列。

任务状态在本机留下什么

04 / 并行

一个 current 任务，也能正常用多个子代理

单 current 限制的是项目顶层同时只有一个主任务，不是只能有一个 Agent。父 Agent 持有这个任务，把工作拆成若干 WorkUnit，分派给子代理；子代理只更新自己的单元，父 Agent 统一合并、验证和关闭。

父任务分派，子代理各做一块

current 是协调边界，不是并发上限；WorkUnit 才是任务内部的并行层。

父 Agent · current 任务 持有执行权 · 拆分 WorkUnit · 分派和解阻 合并代码 · 整体验证 · 写任务级检查点 · 关闭任务
↓
WorkUnit A 后端 · 运行中 令牌过期分支 只写本单元
WorkUnit B 前端 · 运行中 错误提示 UI 只写本单元
WorkUnit C 测试 · 阻塞 等待接口约定 阻塞原因写在单元里
父 Agent 先有 current 任务并拿到执行权；子代理不各自 resume 主任务，也不创建第二个 current。

正常用法是“父 Agent 编排，子代理执行”。父 Agent 先确认当前任务的目标、验收和文件边界，再按可独立交付的部分创建 WorkUnit：每个单元写清楚 owner、负责范围、要交付什么、怎么验证。子代理拿到任务 ID 和单元 ID 后，只更新自己的进度、阻塞和验证结果；不要改任务状态、验收或别人的单元。

子代理完成后，父 Agent 读所有单元，解决冲突，合并代码，跑整体测试，再写任务级检查点。子代理的局部测试通过，不等于任务验收通过；只有父 Agent 能关闭任务。这样项目层始终只有一个 current，并行发生在任务内部，不会出现多个主任务互相抢上下文。

WorkUnit 保护记录，不保护文件。拆并行时优先选互不重叠的文件或 worktree；如果多个子代理必须改同一文件，就串行，或者先分叉工作树再合并。与原任务无关的工作不要硬塞进 WorkUnit，走 side 任务；side 任务不占主队列。

一个具体例子：current 是“登录失败提示”。父 Agent 拆成后端过期分支、前端提示 UI、回归测试三个 WorkUnit，分别交给三个子代理；父 Agent 保留验收和关闭权，最后合并、跑测试、写检查点。子代理只负责自己那一块，不需要知道其他单元的全部细节。

一句话：单 current 是项目层的协调边界；任务内部用 WorkUnit 分派子代理，父 Agent 负责合并、验证和关闭。

05 / 收束

任务结束后，项目经验和用户经验分别怎么产生

任务关闭只说明这次工作结束，不会自动产生长期知识。任务里的发现、失败和验证，先要经过一次独立的证据审查：值得复用的结论写成候选，确认后才生效。项目经验和用户经验走同一条审核路径，但来源、范围和复用方式不同。

两条来源，同一套审核

项目经验来自任务证据；用户经验来自用户明确要求。两者都不能跳过候选和审查。

项目经验 · 同项目复用

任务里的目标、失败、验证和检查点是原材料。任务结束后，审查出值得复用的结论，写成项目候选；确认生效后，后续同类任务可以召回。

任务证据→ 审查→ 候选→ 生效

项目经验默认只在同一项目内复用，不自动进入其他项目。

用户经验 · 跨项目偏好

只有用户明确要求长期记住的偏好或规则，才会产生用户经验。它不能从项目事实自动推断，也不能拿项目结论冒充用户偏好。

用户明确要求→ 审查→ 候选→ 生效

用户经验可以跨项目，但只有显式开启用户偏好时才进入上下文，不是默认注入。

两条路共享同一套状态：候选不进入默认上下文；显式审核后生效，才进入默认召回；退役后退出默认召回但保留记录。任务、检查点和并行单元都不能直接升级为知识。

例如：一次“登录失败提示”的任务，审查后可能留下“错误提示要区分原因”这条项目经验；而“以后所有项目都用中文回复”只能来自用户明确要求，不能从某次任务推断。两者都要先候选、再显式审核，区别只是作用范围和复用边界。

一句话：项目经验从任务证据来，用户经验从用户明确要求来；两条路都不能跳过候选和审查。

06 / 召回

恢复时，AI 从哪儿找回进度，凭什么相信它

新会话、压缩后或换客户端恢复时，MemWeave 不会把全部历史塞回去。它从本机记录里按优先级装回当前任务的最小上下文，并尽量让每条内容都能追溯来源、判断是否过期。

一次恢复按顺序装回什么

任务 brief 有硬下限；后面的内容按剩余空间裁剪，截断会明确标注。

1. 当前任务 目标、验收、下一步；恢复摘要回答“在哪、已完成、失败、下一步”
2. 并行进度 WorkUnit 的进展、阻塞和验证；任务知道哪些子代理卡住了
3. 相关知识 按任务标题/目标或本次 query 检索，只装生效知识；没有匹配就不装
4. 代码结构 架构和文件证据；帮助判断知识是否还适用，不替代真实代码
任务 brief 恢复摘要 WorkUnit 相关知识 结构证据

示意比例，不是真实测量；真实预算是 500–32000 字符，默认 12000。任务 brief 不能被挤出。

这些内容从哪里来

不是从模型记忆里“想起来”，而是从三类本机数据里取。

层里面是什么在召回里的作用权威性
Markdown 记录 任务、检查点、阶段、并行单元、知识正文和来源 最终读到的内容；带 revision/etag 权威记录
SQLite FTS5 索引 从 Markdown 建出的全文索引 按 query、项目、范围、状态找候选 派生索引，可重建
项目结构图 文件哈希、架构节点、扫描时间 判断知识是否还适用于当前代码 支撑证据，不是结论
召回路径：任务标题/目标或本次 query → SQLite 索引找候选 → 回到 Markdown 读当前记录 → 结构图核对是否过期 → 装进上下文。

检索实际怎么走

恢复时，任务、检查点和并行单元不是“搜”出来的，而是按当前任务 ID 直接读 Markdown：任务正文保存最新状态，检查点保留历史顺序。只有知识需要检索：用任务标题/目标或本次 query 去 SQLite FTS5 索引找候选，索引按笔记类型、项目、范围和状态过滤；默认只查生效知识，候选和退役不会返回。索引返回文件路径和分数，最终仍回 Markdown 读当前记录，所以索引不是第二份事实来源。

产品能保证

默认只召回同一项目的生效知识，用户偏好等可选内容必须显式开启；候选和退役不进来；每条结果回读当前 Markdown 和 revision/etag；索引损坏可重建；没有匹配就不注入兜底；截断会明确标注。

产品不能保证

知识是否仍然正确、是否还适用于当前代码、同义词或跨语言是否能召回。这些要靠来源/证据、结构图新鲜度和实际代码/测试核对；搜索命中不等于事实成立。

所以“召回”不是把记忆倒出来，而是：从 Markdown 取当前事实，用 SQLite 索引找相关候选，用结构图判断是否过期，最后把最小上下文交给 Agent；Agent 仍然要用现实核对。

一句话：Markdown 是权威记录，SQLite 是找候选的派生索引；召回负责找得准、带得少，最后是否正确仍要回到代码和测试核对。

07 / 接入

接入之后，一次会话是怎么运行的

MemWeave 不是另一个要你打开的页面。你照常在客户端里打开项目、开始对话；启动通道先让 Agent 接上这个项目的当前任务，然后才进入工作。不同客户端只是启动方式不同，任务和知识模型不变。

完整接入 = MCP 核心 + Skill/Rule 行为契约 + 可工作的启动通道；只有工具只能算已连接。

完整接入的三层

只有 MCP 工具时，只能算“已连接”，不能算完整体验。

启动通道 Hook / always-on Rule / 手动首轮指令
↓
行为契约 Skill：何时恢复、检查点、收尾、提炼
↓
MCP 核心 22 工具、任务/知识模型、项目身份

用一个真实任务走一遍

项目 C:\code\A · 当前任务「登录失败时没有提示」· 下一步「补令牌过期分支」

Hook / Rule 触达 会话开始 · 压缩 · 中断 · 结束 只在边界
MCP / Skill 触达 首轮准备 · 检查点 · WorkUnit · 收尾 · 知识审查 任务内持续

有 Hook 的宿主由 Hook 触达边界；没有 Hook 的宿主由 always-on Rule 或手动首轮指令触达。任务内的持续部分始终走 MCP / Skill。

箭头按时间从上到下发生；移动端可横向滑动查看。

这张图里，启动通道只出现两次：开始会话、压缩后恢复；中间的任务读取、检查点写入都走 MCP。Hook 不保存任务，MCP 也不会主动叫醒模型。

继续这个例子：用户隔天打开同一个项目，Agent 先调用准备动作，看到“补令牌过期分支”；再核对代码和测试，发现这个分支已经改过、测试也通过了，于是把下一步更新为“补网络异常分支”，而不是让用户重新解释或重做一遍。

所以 Hook 不是存储，也不是每轮都跑；它只在起点和压缩边界负责把 Agent 叫醒。行为契约负责规定什么时候准备、什么时候写检查点、什么时候收尾；MCP 核心负责真正读写任务、检查点和知识。没有 Hook 的客户端也能用同一套流程，只是启动和压缩恢复由 always-on Rule 或手动首轮指令完成。

一句话：启动通道只在起点和压缩边界叫醒；行为契约规定工作循环；MCP 核心负责真正读写。一次会话就是这三层在同一条时间线上的配合。
