MemWeave 贯穿项目的整个生命周期

AI 推进一个项目时，上下文会满、会话会换、工具也会换。MemWeave 把任务做到哪、试过什么、下一步做什么记在本机，并把值得复用的经验沉淀下来，让下一次能接着干。

MemWeave
00 优势 01 项目 02 任务 03 记录 04 并行 05 审查 06 召回 07 接入

00 / 优势

长任务不跑偏，项目和经验都能接上

推进一个长任务时，上下文会越来越长，还会经历多次压缩。AI 可能忘记目标、重复试错，甚至偏离方向；如果中途换了会话或客户端，任务状态又断了。

三个直接好处

一个解决长任务跑偏，一个解决换会话/客户端断线，一个解决经验留不下来。

01 长任务不跑偏

任务做久了，AI 容易忘记目标、重复试错，甚至被中间细节带偏。

MemWeave 把目标、失败和下一步记在本机，每次压缩或新会话后都带回来，减少这种偏移。

长上下文→ 多次压缩→ 目标 / 失败 / 下一步

02 项目记忆跨会话、跨客户端

项目原本在一个工具里推进，下一次开新会话，或换到另一个 MCP 客户端，仍然接着同一个项目、同一个任务。

不需要重新解释目标、进度和失败；换的是工具或会话，不是任务。

工具 A→ 工具 B→ 同一个任务

同一个项目，同一个任务。

03 任务沉淀经验，用户记忆跨项目

每个任务结束时先做一次删选：绝大多数内容留在任务记录，只有值得跨任务复用的结论才沉淀为项目经验；下次遇到类似工作，可以直接复用，不用重新摸索。

用户明确要求保留的偏好或经验，可以跨项目使用；只有显式启用才进入上下文。

任务结束→ 证据审查→ 项目经验

用户记忆：跨项目，显式启用。

一句话：MemWeave 不替你写代码。它把任务的目标、失败和下一步记在本机，让 AI 在长任务压缩后、换会话或换客户端时仍然能接着做；任务结束后，还能把项目经验沉淀下来。

01 / 项目

项目就是你打开的那个文件夹

多个客户端能接上同一个项目，前提是它们认的是同一个项目身份。项目身份不是客户端账号，也不是聊天会话，而是你打开的那个绝对文件夹。同一个文件夹，不管从哪个工具打开，都是同一个项目；在该文件夹下打开任意子目录，也归到同一个项目。

项目身份跟着文件夹走

客户端只是读取入口；同一个文件夹，不管从哪个工具打开，都是同一个项目。

不同客户端 AI 工具 A AI 工具 B AI 工具 C
→
同一个文件夹 绝对路径 = 项目身份 C:\code\A
→
同一个项目 任务 / 检查点 / 阶段 / 知识 换客户端，不换项目

项目之间的边界

项目之间默认互不读取；worktree 是同一个项目的执行别名，不同 clone 是另一个项目。

MemWeave 不按目录层级推导项目之间的关系。每个已登记项目只读自己的任务和知识；需要跨项目复用经验时由用户显式操作，默认不注入。项目移动到新路径后，通过一次重登记或路径映射把它接回同一项目身份。

一句话：一个文件夹就是一个项目，子目录属于它；项目之间没有隐式层级，也不默认共享记忆。

02 / 任务

一次只推进一个主任务

任务不是一条待办，而是一份可恢复的契约：目标、验收、阶段、下一步和契约摘要。顶层任务顺序化，任务内部才并行；无关工作走侧任务，不抢主队列。

任务状态机

新任务进入 current 或 queued；current 完成后进入 completed，审查后归档；queued 在 current 关闭后补位。

side 侧任务

不进入主队列；完成后同样进入 completed 审查，取消后直接归档；关闭时不影响 current / queued。

phase 收束

只是阶段边界，current 不变，不关闭任务。

同一时间只有一个主任务。已有主任务时，新目标先排队；主任务完成或取消后，排在最前面的任务自动接上。侧任务有自己的目标、验收和进度，但不占主队列；阶段收束只结束一个阶段，任务状态不变。目标和验收被外部改动时，系统会提示先确认，不会悄悄按旧目标继续。

一句话：顶层任务顺序化，任务内部才并行；无关工作走侧任务，不抢主队列。

03 / 记录

任务状态在本机留下什么

创建任务时有一个任务文件，执行中按需留下检查点，阶段、并行单元和知识各自另存。任务文件保留最新状态，检查点文件保留历史快照。

04 / 并行

一个 current 任务，也能正常用多个子代理

单 current 限制的是项目顶层同时只有一个主任务，不是只能有一个 Agent。父 Agent 持有这个任务，把工作拆成若干 WorkUnit，分派给子代理；子代理只更新自己的单元，父 Agent 统一合并、验证和关闭。

父任务分派，子代理各做一块

current 是协调边界，不是并发上限；WorkUnit 才是任务内部的并行层。

父 Agent · current 任务 持有执行权 · 拆分 WorkUnit · 分派和解阻 合并代码 · 整体验证 · 写任务级检查点 · 关闭任务
↓
WorkUnit A 后端 · 运行中 令牌过期分支 只写本单元
WorkUnit B 前端 · 运行中 错误提示 UI 只写本单元
WorkUnit C 测试 · 阻塞 等待接口约定 阻塞原因写在单元里
父 Agent 先有 current 任务并拿到执行权；子代理不各自 resume 主任务，也不创建第二个 current。

正常用法是“父 Agent 编排，子代理执行”。父 Agent 先确认当前任务的目标、验收和文件边界，再按可独立交付的部分创建 WorkUnit：每个单元写清楚 owner、负责范围、要交付什么、怎么验证。子代理拿到任务 ID 和单元 ID 后，只更新自己的进度、阻塞和验证结果；不要改任务状态、验收或别人的单元。

子代理完成后，父 Agent 读所有单元，解决冲突，合并代码，跑整体测试，再写任务级检查点。子代理的局部测试通过，不等于任务验收通过；只有父 Agent 能关闭任务。这样项目层始终只有一个 current，并行发生在任务内部，不会出现多个主任务互相抢上下文。

WorkUnit 保护记录，不保护文件。拆并行时优先选互不重叠的文件或 worktree；如果多个子代理必须改同一文件，就串行，或者先分叉工作树再合并。与原任务无关的工作不要硬塞进 WorkUnit，走 side 任务；side 任务不占主队列。

一个具体例子：current 是“登录失败提示”。父 Agent 拆成后端过期分支、前端提示 UI、回归测试三个 WorkUnit，分别交给三个子代理；父 Agent 保留验收和关闭权，最后合并、跑测试、写检查点。子代理只负责自己那一块，不需要知道其他单元的全部细节。

一句话：单 current 是项目层的协调边界；任务内部用 WorkUnit 分派子代理，父 Agent 负责合并、验证和关闭。

05 / 收束

任务结束后，知识由谁审、何时审、按什么标准审

任务关闭只说明这次工作结束，不会自动产生长期知识。MemWeave 只准备证据包、lint 和晋升门槛；宿主 Agent 负责判断，用户保留最终审计权。任务里的发现、失败和验证，先要经过一次独立的证据审查：**默认结论是删除**，只有确实跨任务复用、删掉后明显更容易重复犯错的结论才写成知识并附来源；不确定或仍待审的内容写成候选，`memory_review_complete` 会在记录审查结果的同一个原子提交里激活本次候选。项目经验和用户经验走同一条审核路径，但来源、范围和复用方式不同。

两条来源，同一套审核

项目经验来自任务证据；用户经验来自用户明确要求。候选只用于不确定或待审内容，审查完成即进入默认召回。

项目经验 · 同项目复用

任务里的目标、失败、验证和检查点是原材料。任务结束后，审查出值得复用的结论，写成项目知识；不确定的内容先写候选，随审查完成一起激活，后续同类任务即可召回。

任务证据→ 审查→ 知识（默认 active）→ 默认召回

项目经验默认只在同一项目内复用，不自动进入其他项目。

用户经验 · 跨项目偏好

只有用户明确要求长期记住的偏好或规则，才会产生用户经验。它不能从项目事实自动推断，也不能拿项目结论冒充用户偏好。

用户明确要求→ 审查→ 候选→ 生效

用户经验可以跨项目，active 用户偏好默认进入上下文；写入用户范围仍要求明确的用户来源。

两条路共享同一套状态：候选不进入默认上下文；审查完成时本次 reviewed 候选被原子激活并进入默认召回；退役后退出默认召回但保留记录。任务、检查点和并行单元都不能直接升级为知识。
晋升门槛：默认删除，不默认保留。 记录必须先证明自己值得留下。只有跨任务仍然稳定、删掉后会明显更容易重复犯错、且证据可回放的规则，才值得晋升。改进文案、压缩长度或“看起来有点用”都不是保留理由；不确定就删除。一次审查写 0 条知识是正常结果。
以下内容直接删除，不做“改进后保留”： 任务进度与收尾总结、版本/发布快照、函数或测试名、文件位置与配置值、一次性冒烟步骤、复述代码或文档、具体业务规则或产品规格、泛泛的最佳实践、未经验证的推断。
保留 ≠ 保留原写法。 通过门槛后必须重写：标题直接写规则；第一句说明适用场景和要做什么；一条只讲一个主题；正文只保留边界、例外和失败模式；证据放进 evidence，不写任务过程、函数名、版本号和测试数量。优先控制在 600 字以内，超过 1200 字进入重写候选；写不短就拆或删。

同一段任务记录，怎样判断该不该留

先判断是否值得保留；不值得就删除，不要改写成一条“看起来像经验”的记录。

删除 · 任务/版本快照

v0.7.6 发布记录：安装包 sha256 9743c434，候选上限 500，批次 10 个，309 项测试通过。

版本号、哈希、参数和测试数量都会过期；未来任务不能据此改变决策。

保留 · 项目不变量

破坏性维护先预览再执行：删除或迁移数据前必须预览并备份；整批异常先视为上游故障，不能据此批量删除。

跨任务、非显而易见、删掉会明显更容易造成数据损失；附代码/测试证据。

审查不是一句话，而是一条状态链

每一段都有明确输入、责任人和输出；任何一段停下来，知识就停在候选，不会进入默认上下文。

闭环不是感觉，而是可观测状态

system_status.knowledge_loop 汇总长期记忆闭环的真实债务和证据，不靠“用了很久应该有效”来判断。

会被暴露的债务

待审任务/阶段龄期、孤立 candidate、迁移激活但未核验的记录、缺失来源、无证据和单来源风险。没有注入追踪时，不回退成“零召回”结论，而是明确标记为未观测。

workspace_prepare 记录本次真正进入 included_sources 的知识；导航索引里只出现标题不算召回证据。

会被验证的行为

behavioral_reuse 场景先制造一次失败，再让同类任务在新会话出现：没有经验时确定性策略选择危险命令，有经验并被作为证据注入时切换到安全路径。

这是确定性策略回放，不是模型成功率证明。另有一个隔离的 scripts/memweave_agent_eval.py 真实 Codex A/B，检查自动准备、included_sources、实际命令和文件结果；单次运行仍不等于统计收益。

一句话：项目经验从任务证据来，用户经验从用户明确要求来；两条路都默认删除，只有通过门槛且证据可回放的规则才留下。

06 / 召回

恢复时，AI 从哪儿找回进度，凭什么相信它

新会话、压缩后或换客户端恢复时，MemWeave 不会把全部历史塞回去。它从本机记录里按优先级装回当前任务的最小上下文，并尽量让每条内容都能追溯来源、判断是否过期。

一次恢复按顺序装回什么

任务 brief 有硬下限；后面的内容按剩余空间裁剪，截断会明确标注。

1. 当前任务 目标、验收、下一步；恢复摘要回答“在哪、已完成、失败、下一步”
2. 并行进度 WorkUnit 的进展、阻塞和验证；任务知道哪些子代理卡住了
3. 相关知识 按任务标题/目标或本次 query 检索 active 知识，并附有界 active-only 知识索引；候选/退役不装
4. 代码结构 架构和文件证据；帮助判断知识是否还适用，不替代真实代码
任务 brief 恢复摘要 WorkUnit 相关知识 结构证据

示意比例，不是真实测量；真实预算是 500–64000 字符，默认 32000。任务 brief 与开放 WorkUnit 不能被挤出，低预算时知识索引先让位。

这些内容从哪里来

不是从模型记忆里“想起来”，而是从三类本机数据里取。

层里面是什么在召回里的作用权威性
Markdown 记录 任务、检查点、阶段、并行单元、知识正文和来源 最终读到的内容；带 revision/etag 权威记录
SQLite FTS5 索引 从 Markdown 建出的全文索引 按 query、项目、范围、状态找候选 派生索引，可重建
项目结构图 文件哈希、架构节点、扫描时间 判断知识是否还适用于当前代码 支撑证据，不是结论
召回路径：任务标题/目标或本次 query → SQLite 索引找候选 → 回到 Markdown 读当前记录 → 结构图核对是否过期 → 装进上下文。

检索实际怎么走

恢复时，任务、检查点和并行单元不是“搜”出来的，而是按当前任务 ID 直接读 Markdown：任务正文保存最新状态，检查点保留历史顺序。只有知识需要检索：用任务标题/目标或本次 query 去 SQLite FTS5 索引找命中，索引按笔记类型、项目、范围和状态过滤；默认只查生效知识，候选和退役不会返回。中文/混合查询在严格匹配无结果时会用原始词项做 OR 兜底；长篇自然中文如果整段短语不命中，会用脚本 unigram/bigram 覆盖回退，要求多个共享片段，避免单字误命中。索引返回文件路径和分数，最终仍回 Markdown 读当前记录，所以索引不是第二份事实来源。

产品能保证

默认召回同一项目的生效知识，并注入 active 用户偏好与有界知识索引；候选和退役不进来；每条命中回读当前 Markdown 和 revision/etag；索引损坏可重建，派生索引未运行时仍返回 Markdown 知识导航并标注 attention；没有匹配就不注入兜底；截断会明确标注。中文/混合查询会先走严格 FTS，再按词项 OR 兜底；长自然中文另走多片段覆盖回退，不要求精确原词复现，也不把单个共享字当命中。

产品不能保证

知识是否仍然正确、是否还适用于当前代码、同义词或跨语言是否能召回。这些要靠来源/证据、结构图新鲜度和实际代码/测试核对；搜索命中不等于事实成立。

所以“召回”不是把记忆倒出来，而是：从 Markdown 取当前事实，用 SQLite 索引找相关候选，用结构图判断是否过期，最后把最小上下文交给 Agent；Agent 仍然要用现实核对。

一句话：Markdown 是权威记录，SQLite 是找候选的派生索引；召回负责找得准、带得少，最后是否正确仍要回到代码和测试核对。

07 / 接入

接入之后，一次会话是怎么运行的

MemWeave 不是另一个要你打开的页面。你照常在客户端里打开项目、开始对话；启动通道先让 Agent 接上这个项目的当前任务，然后才进入工作。不同客户端只是启动方式不同，任务和知识模型不变。

完整接入 = MCP 核心 + Skill/Rule 行为契约 + 可工作的启动通道；只有工具只能算已连接。

这张图里，启动通道只出现两次：开始会话、压缩后恢复；中间的任务读取、检查点写入都走 MCP。Hook 不保存任务，MCP 也不会主动叫醒模型。

继续这个例子：用户隔天打开同一个项目，Agent 先调用准备动作，看到“补令牌过期分支”；再核对代码和测试，发现这个分支已经改过、测试也通过了，于是把下一步更新为“补网络异常分支”，而不是让用户重新解释或重做一遍。

所以 Hook 不是存储，也不是每轮都跑；它只在起点和压缩边界负责把 Agent 叫醒。行为契约负责规定什么时候准备、什么时候写检查点、什么时候收尾；MCP 核心负责真正读写任务、检查点和知识。Codex 的首轮启动由受管 AGENTS.md 保证，Cursor/Devin 由 always-on Rule 或手动首轮指令完成；Hook 只作为边界增强，不能单独证明模型已收到启动上下文。

一句话：启动通道只在起点和压缩边界叫醒；行为契约规定工作循环；MCP 核心负责真正读写。一次会话就是这三层在同一条时间线上的配合。
